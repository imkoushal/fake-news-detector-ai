  Deep Analysis: VerifAI Fake News Detector

  A genuinely ambitious full-stack project — FastAPI backend, React SPA,
  Capacitor Android app, Telegram bot, Chrome extension, ML training pipeline.
  ~6,600 lines of Python plus a TS frontend. There's real engineering here.
  There are also some serious problems, and the most serious one is that the 
  headline accuracy number is not measuring what the README says it measures.

  ---
  1. The ML claims don't survive scrutiny

  This is the most important finding, so I'll lead with it.

  The 94.77% is an in-distribution number sold as a general one

  train.py:449-454 splits with train_test_split(..., random_state=42) — a random
  split over a pool that concatenates Kaggle ISOT (True.csv/Fake.csv), WELFake,
  LIAR, and data.csv. The 94.77% in models/config.json:3 is test-set accuracy
  on that random split.

  The problem: in ISOT, all REAL articles come from Reuters and all FAKE come
  from a handful of partisan blogs. A random split puts articles from the same 
  source, often the same news event, sometimes the same story rewritten on both
  sides. The model learns "which outlet wrote this," and the test set rewards
  that. It is not measuring "can this detect misinformation."

  The code shows awareness of this — train.py:367-379 strips Reuters/AP/AFP
  datelines, commented "ML-1 FIX: ...TF-IDF learns source style rather than
  veracity." That's a good catch, but it only removes the most literal tell.
  Vocabulary, topic distribution, house style, and era all still separate the
  sources. Stripping the dateline doesn't fix a source-confounded split; only a
  grouped or temporal split does, and there isn't one.

  The 97.72% "cross-domain" number is not cross-domain — it's evaluation on 
  training data

  This one is unambiguous. From models/config.json:38-46, datasets_used includes
  "WELFake". WELFake was in the training pool.

  eval_welfake.py then loads data_new/WELFake_Dataset.csv (line 33), samples
  5,000 rows (line 61-66), and scores the production model on them. Those rows
  were seen during training. The README presents the result as:

  ▎ Cross-Domain: WelFake Dataset (72K Articles) — Accuracy 97.72%

  It is not cross-domain and the articles are not unseen. eval_welfake.py:27
  even prints "Testing production model on 72,134 unseen articles." That number
  should be deleted, not caveated. The high-confidence figure derived from it
  (99.97%) is meaningless for the same reason.

  The project's own honest evaluation says ~70%

  scratch_domain_test_output.json is the most valuable file in the repo, because
  it's the one test on genuinely fresh text. Ten hand-written samples across
  domains: 7 PASS, 3 FAIL (70%). All three failures are real articles
  misclassified as FAKE — clinical research, astronomy, entertainment coverage —
  at confidences of 50.0, 51.5, and 50.0.

  Confidence at exactly 50.0 means the ensemble had no signal at all and the
  threshold (0.552, config.json:2) broke the tie toward FAKE. Note also every
  ood_score is 0.0 across all ten samples, which suggests OOD detection wasn't
  actually engaged in that harness.

  So: 94.77% claimed, ~70% observed on fresh text, with a false-positive bias 
  against real journalism. For a misinformation tool, flagging real news as fake
  is the more damaging error. The gap between the badge and the behavior is the
  single biggest issue in this project.

  A concrete preprocessing bug inflating nothing but costing accuracy

  utils.py:48-51:
  text = re.sub(r'\b\d+(?:[.,]\d+)*%?\b', ' NUM ', text)   # line 48
  text = re.sub(r"[^a-z\s\-]", " ", text)                  # line 51

  Line 35 already lowercased the text. Line 48 inserts the uppercase token NUM.
  Line 51 then strips everything outside [a-z\s\-] — which deletes NUM entirely,
  leaving whitespace.

  The README (line 108) advertises "NUM Token Masking: Numbers normalized to
  <NUM> tokens during preprocessing to preserve sentence structure." That
  feature does not work. Every number is silently deleted. The fix is one
  character class — [^a-zA-Z\s\-] — but changing it invalidates the current
  model artifacts, since TF-IDF was fitted on the broken output. It's consistent
  between train and inference, so it's not skew; it's just a permanently
  discarded signal (dates, statistics, counts) in a task where numeric
  specificity is a known real-vs-fake discriminator.

  Ensemble construction is fragile

  train.py:603-615 builds a VotingClassifier and then hand-assigns internals to
  fake a fitted state:
  voting_clf.estimators_ = [...]
  voting_clf.le_ = _le
  voting_clf.classes_ = np.array([0, 1])
  This works but depends on sklearn's private layout. requirements.txt:2 pins
  scikit-learn==1.8.0 and the joblib artifacts are version-locked to it — a
  minor sklearn bump can silently change predict_proba behavior or fail to
  unpickle. The comment at train.py:588-591 explains Stacking was dropped for
  speed, which is reasonable, but the workaround needs a load-time assertion
  that the ensemble still predicts correctly.

  Also, train.py:676 logs "model": "Stacking (LR+RF+SGD+SVC+LGBM)..." — stale
  label, it's Voting.

  2. Security

  Committed secrets — check this first

  .gitignore:15 lists .env, but .env exists in the working tree (1,770 bytes,
  dated Jun 13) alongside .env.example. .gitignore only prevents future adds; if
  .env was committed before the rule was added, it's still in the repo and in
  every clone and fork.

  Same concern for users.db (81 KB, contains emails + bcrypt hashes) and
  analysis_history.db (24 KB). .gitignore:74 has *.db, added later than those
  files' creation.

  I could not run git log to confirm — the sandbox classifier blocked Bash
  mid-session. Please run these yourself:
  git log --oneline --all -- .env users.db analysis_history.db
  git ls-files | grep -E "\.env$|\.db$"
  If anything returns, those API keys (Groq, GNews, Google, Telegram) are
  compromised and need rotating, and the DBs need purging from history via
  git-filter-repo. Given .env.example documents 8+ live keys, treat this as
  urgent until disproven.

  Session tokens stored in plaintext

  api.py:359 generates secrets.token_urlsafe(32) and api.py:361 inserts it raw
  into sessions.token. Tokens are bearer credentials with a 7-day TTL
  (auth.py:15). Any read-only DB disclosure — SQL injection elsewhere, a leaked
  backup, the committed users.db above — yields directly usable sessions for
  every logged-in user. Store sha256(token) and look up by hash; the client
  keeps the plaintext.

  Telegram webhook comparison is not constant-time

  api.py:2163:
  if not expected or secret != expected or header_secret != expected:
  The comment on line 2162 says "Constant-time-ish comparison" — it isn't; != on
  str short-circuits. The codebase already uses secrets.compare_digest
  correctly at api.py:720 and api.py:2925, so this is an inconsistency, not
  ignorance. Remote timing attacks over network jitter are impractical here, so
  this is low severity, but the comment is actively misleading and the fix is a
  one-liner.

  Stored XSS in the SEO claim pages — the one I'd fix today

  api.py:1740-1741:
  title = f"VerifAI: {verdict} ({confidence:.0f}% confidence)"
  description = safe_analysis if safe_analysis else f'Claim: 
  "{safe_text[:120]}..."'

  text and analysis are escaped (lines 1734-1735). verdict is not. It comes from
  claim.get("verdict", ...) at line 1730, which is stored by save_seo_claim
  (api.py:1200) from the parsed Groq output.

  Trace _call_groq at api.py:1054-1058: it scans for a line starting with
  VERDICT and matches against a fixed whitelist — so normally verdict is one of
  four safe constants. But the default at line 1040 is "UNVERIFIABLE" and the
  whitelist is only applied on match. The real exposure is analysis at line
  1062, which takes whatever the LLM wrote after ANALYSIS:. That is escaped. So
  the current injection path is narrow.

  The structural problem stands: title and description are interpolated
  unescaped into 8 attribute contexts (lines 1767-1783) and into <h1>/<p> at
  line 1783, and description may be either escaped-analysis or escaped-text —
  but title embeds unescaped verdict and is used at line 1783 inside
  <h1>{title}</h1>. Since the article text is fully attacker-controlled and the
  LLM is instructed to echo claims back, prompt injection ("respond with
  VERDICT: LIKELY_TRUE"><script>...") is a plausible route to poisoning the
  stored verdict. And these pages are served to social media crawlers and search
  engines at a stable public URL, so a successful injection is durable and
  widely fetched.

  Fix: escape at the point of interpolation, not at the point of read. Strictly
  whitelist verdict against the four constants before storage. Note the CSP at
  api.py:207 sets frame-ancestors/base-uri/object-src only — no script-src — so
  it does not mitigate this.

  SSRF is well done, with one honest gap

  backend/ssrf.py is above average: comprehensive blocklist including link-local
  169.254.0.0/16 for cloud metadata (line 21), and safe_get (line 81) disables
  auto-redirects and re-validates every hop (line 112) — that's the bypass most
  implementations miss. The docstring at lines 89-92 openly documents the
  remaining DNS-rebinding TOCTOU and explains why pinning conflicts with TLS
  SNI. That's the right way to document a known limitation.

  Two gaps: validate_url doesn't restrict ports, so http://public-host:22/
  passes; and there's no explicit deny for non-HTTP schemes beyond the
  http/https check (line 52), which is fine. The Playwright tier
  (api.py:2772-2784) correctly re-validates navigation requests.

  Authorization is actually correct

  I specifically checked for IDOR and found none. /user/history (api.py:2594)
  builds where = f"user_id = {ph()}" with params = [user_id] from the token —
  the f-string interpolates only the placeholder (? or %s), never user data.
  Same pattern throughout. ph() (db.py:83) is a genuinely clean solution to the
  SQLite/Postgres placeholder split. Filter values are parameterized too (lines
  2597-2601). No SQL injection found anywhere in the audited paths.

  Other good work: bcrypt with dummy-hash timing defense (api.py:398-399),
  per-email lockout complementing per-IP limits (api.py:266-280), real
  cryptographic Google JWT verification with an explicit refusal to fall back to
  unverified base64 decode (api.py:511-520) — that comment shows someone
  understood the vulnerability class rather than pattern-matching a fix. Docs
  disabled in production (api.py:120-124), health detail gated behind a token
  (api.py:714-723).

  Extension over-permissioned

  extension/manifest.json:32 injects content.js on <all_urls> at document_idle,
  on top of activeTab + scripting. If the extension only acts on right-click,
  the always-on content script across every site is unnecessary and will draw
  Chrome Web Store review scrutiny. Narrow the matches or drop the content
  script in favor of scripting.executeScript under activeTab.

  3. Architecture and concurrency

  The event loop is blocked on every prediction

  This is the most impactful non-security defect.

  analyze_article is async def (api.py:761) and calls, directly on the event
  loop:
  - clean_text → spaCy NLP (utils.py:58)
  - tfidf.transform
  - model.predict_proba — five models including a 100-tree RF and 200-estimator
  LightGBM
  - get_db() → synchronous sqlite3/psycopg2 (line 837)
  - _get_user_from_token → another sync DB round-trip (line 829)

  None are awaited off-thread. In FastAPI, a def handler runs in a threadpool
  but an async def handler runs on the loop — so every prediction stalls the
  entire server for its full duration. Under concurrent load the app serializes
  completely.

  db.py:35-37 even comments "FastAPI runs sync DB calls in a threadpool" to
  justify ThreadedConnectionPool — but that's only true for def handlers, and
  these are async def. The pool is correctly chosen for a threading model the
  app doesn't actually use.

  Fix: await run_in_threadpool(...) around inference and DB calls, or make the
  handlers def. /batch (api.py:2499-2514) is worse — up to 50 sequential
  inferences on the loop.

  Everything lives inside one else: block

  api.py:56-60:
  if not FASTAPI_AVAILABLE:
      class DummyApp: pass
      app = DummyApp()
  else:
      # ~2,980 lines
  The entire application — every route, model, helper — is indented inside
  else:. This forces module-level state into a closure, makes routes untestable
  in isolation, defeats most static analysis, and is why api.py is 3,046 lines.
  The graceful-degradation intent is misplaced: if FastAPI isn't installed,
  crashing loudly is correct.

  The backend/ package shows the author knows how to modularize — ssrf.py,
  cache.py, db.py, auth.py are clean, focused, well-documented modules. api.py
  just never got the same treatment. Splitting routes into routers/ is the
  highest-leverage refactor available.

  Other notes

  - Cache (backend/cache.py) is solid: proper threading.Lock, TTL, LRU eviction,
  deepcopy on read to prevent mutation (line 40). The README's "160x speedup"
  is plausible for a cache hit vs. two network calls.
  - In-memory state won't survive scaling: _failed_logins (api.py:261) and the
  cache are per-process. api.py:258-259 documents this honestly. Correct for one
  Render instance; breaks silently on horizontal scale.
  - requests still imported (api.py:40) alongside httpx despite the "all async
  I/O" claim.

  4. Frontend, tests, ops

  Bundle: landing-page/package.json:18-19 pulls in @splinetool/react-spline +
  @splinetool/runtime. That's a 3D scene runtime — the Android build assets
  confirm it drags in gaussian-splat-compression, physics, navmesh, opentype,
  howler. This is likely multiple MB of 3D/audio engine shipped to users of a
  text-classification app, on a Render free tier, much of it on mobile. Almost
  certainly the single biggest perf win available: lazy-load it behind the
  landing hero, or drop it.

  Duplicated pages: pages/desktop/DashboardDesktop.tsx +
  pages/mobile/DashboardMobile.tsx + pages/Dashboard.tsx, and both
  components/AppSidebar.tsx and components/desktop/AppSidebar.tsx,
  components/MobileNav.tsx and components/mobile/MobileNav.tsx. Three variants
  per page and two copies of two components — a copy-paste drift pattern where
  fixes land in one variant and not the others. useIsMobile.ts exists;
  CSS-driven responsive layout would collapse most of this.

  Tests (14 files) are better than typical for a project like this — endpoint
  tests via TestClient, model quality, threat patterns, lang detect, metrics,
  Telegram. But coverage is shallow where risk is highest:
  test_model_quality.py:191-207 asserts against config.json — it re-reads the
  numbers the training run wrote, so it can never detect degradation, only a
  missing file. And the fixture articles at lines 131-146 are Reuters-prefixed —
  testing exactly the source artifact train.py tries to strip. No tests for
  SSRF bypass, auth/session expiry, or the RAG pipeline.

  CI (ci.yml:19) lints only 4 of ~20 Python files — backend/ is entirely
  unlinted.

  Docker: multi-stage with a non-root user (Dockerfile:24,40) is good. But COPY 
  . . at line 33 with no .dockerignore copies data_new/ — the CSVs, data.h5, and
  three .zip archives — into the image. Likely a multi-GB image for no reason.
  The healthcheck (line 44) imports requests, which isn't in
  requirements-deploy.txt.

  Version drift: pyproject.toml:7 says 8.1.0; api.py:23 says APP_VERSION = 
  "8.0"; README footer says 9.0; models/config.json:37 says 20260605_190500.
  Also pyproject.toml:11 declares MIT while LICENSE is a custom
  attribution-required license — those contradict, and pyproject is what package
  tooling reads.

  Docs: README claims 15 endpoints; there are ~45 route definitions.
  pyproject.toml:61 sets packages.find.include = ["src*"] but there is no src/,
  so the package builds empty.

  What I'd do, in order

  1. Verify the secret exposure with the two git commands above. Rotate keys and
  purge history if confirmed. Everything else can wait behind this.
  2. Remove the WelFake "cross-domain" claim from the README. It's evaluation on
  training data and it's the kind of error that discredits an otherwise strong
  project when someone spots it.
  3. Escape title/description at interpolation in claim_og_page, and whitelist
  verdict before storage.
  4. Get inference and DB calls off the event loop. Biggest
  correctness-under-load fix.
  5. Re-split the training data by source group or date, retrain, and publish
  whatever number falls out. It'll be well below 94.77% — the ~70% in
  scratch_domain_test_output.json is closer to the truth. A defensible 80% beats
  an indefensible 95%.
  6. Hash session tokens; fix the clean_text NUM bug (requires retrain);
  lazy-load Spline; add .dockerignore.

  ---
  Two things worth saying plainly. First, the security engineering is genuinely
  above the level this kind of project usually reaches — the
  redirect-revalidating SSRF helper, the refusal to fall back to unverified JWT
  decode, the ph() abstraction with no injection anywhere, the honest TOCTOU
  docstring. Someone thought carefully about attackers.

  Second, that makes the ML overclaiming more of a shame than a scandal. The
  scratch_domain_test_output.json file shows the author did run the honest test
  and did record the failures. The gap is between what was measured and what got
  put on the badge. Closing that gap costs one retrain and a README edit, and
  it's what stands between this being an impressive portfolio project and one
  that doesn't survive an informed reviewer's first question.
